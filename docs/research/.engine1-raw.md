BLUF: Every shipping system converges on the same mechanism: a per-scanner allowlist of stable identity fields, hashed into a fingerprint, with run-varying data excluded by construction rather than by cleanup. DefectDojo is the reference implementation you can lift directly (BSD-3-Clause), including its human-curated field map for ~150 scanners. The false-FIXED failure mode is not solved by better hashing; it is solved by making "FIXED" the conclusion that requires the strongest evidence (a trusted per-parser identity), and defaulting every un-vetted parser to "cannot assert fixed."

## F1. DefectDojo — the canonical model, and the one to copy

Four named algorithms (`dojo/settings/settings.dist.py`):

- `legacy` — compares a fixed attribute set: title, cwe, line, file_path, description, plus endpoints. Dynamic findings require endpoints to match strictly; static findings allow superset endpoints. If endpoints, file_path and line are all empty it refuses to dedupe (fails safe: no match rather than a false one).
- `hash_code` — SHA-256 of the concatenated values of fields named in `HASHCODE_FIELDS_PER_SCANNER[parser]`, in the order they appear in `HASHCODE_ALLOWED_FIELDS`, with `HASH_CODE_FIELDS_ALWAYS = ["service"]` appended for all scanners.
- `unique_id_from_tool` — trusts a stable id the scanner itself emits; endpoints ignored.
- `unique_id_from_tool_or_hash_code` — match if either matches.

The two config dicts are the asset: `HASHCODE_FIELDS_PER_SCANNER` (which fields identify a finding, per scanner) and `DEDUPLICATION_ALGORITHM_PER_PARSER` (which of the four algorithms to use, per scanner). A WebFetch read of the raw file reports roughly 150+ scanners in the first and 160+ parsers in the second (medium confidence on the exact count; the structure is certain). `HASHCODE_ALLOWED_FIELDS` is the whitelist of fields a scanner is even *allowed* to hash: title, cwe, cwes, vulnerability_ids, line, file_path, payload, component_name, component_version, description, endpoints, unique_id_from_tool, severity, vuln_id_from_tool, mitigation. Configurable via `settings.dist.py` or the `DD_HASHCODE_FIELDS_PER_SCANNER` env var as JSON.

Documented guidance that maps straight onto your failure mode: their docs warn that title and description "tend to change when the tools evolve" so they weaken cross-scanner dedup, and that adding severity keeps dedup from being "too aggressive." The whitelist exists precisely so a parser cannot inject an arbitrary field into identity. Note what is NOT in the allowlist: byte sizes, timestamps, scan duration, list index. That exclusion is the whole defense against your false-FIXED bug.

Reimport / reactivation semantics (this is the false-remediation surface): reimport matches incoming findings by `hash_code` or `unique_id_from_tool`. A closed finding that reappears is automatically reopened. A finding present before but absent from the new report is set Inactive+Mitigated only when `close_old_findings=True` (default on in UI). This is exactly where false FIXED is manufactured, and DefectDojo has a live cluster of bugs proving it: #8100 (identical reimport wrongly mitigates), #12754 ("Critical: findings wrongfully marked Inactive, Verified, Mitigated"), #8797. The common root: triage-less scanners (Trivy named explicitly) whose output varies run to run, so the hash shifts and the old finding looks gone. Documented limit: OSS DefectDojo makes no claim of reliable cross-scanner dedup; that is a Pro-only feature ("Global Component / Global Locations").

Sources: [Deduplication Algorithms](https://docs.defectdojo.com/en/working_with_findings/finding_deduplication/deduplication_algorithms/), [About Deduplication](https://docs.defectdojo.com/triage_findings/finding_deduplication/about_deduplication/), [Deduplication Tuning](https://docs.defectdojo.com/en/working_with_findings/finding_deduplication/deduplication_tuning_os/), [Reimport](https://docs.defectdojo.com/import_data/import_intro/reimport/), [settings.dist.py](https://github.com/DefectDojo/django-DefectDojo/blob/master/dojo/settings/settings.dist.py), [issue #8100](https://github.com/DefectDojo/django-DefectDojo/issues/8100), [issue #12754](https://github.com/DefectDojo/django-DefectDojo/issues/12754), [issue #1500 make dedup per-parser](https://github.com/DefectDojo/django-DefectDojo/issues/1500).

## F2. SARIF 2.1.0 — fingerprints vs partialFingerprints, and how GitHub actually uses them

`result.fingerprints` (§3.27.16) is a "stable value that can be used by a result management system to uniquely identify a result over time, even if a relevant artifact is modified." `result.partialFingerprints` (§3.27.17) are weaker components used to match logically-equivalent results when line numbers or positions shift. Both use versioned keys ("name/v1") so the algorithm can evolve without colliding with old data. Appendix B is normative on how a result management system compares a run to a baseline to classify new vs persistent. The spec deliberately steers identity toward algorithmic hashes of *content*, not position.

GitHub code scanning is the concrete implementation: it uses only `partialFingerprints.primaryLocationLineHash`. If a SARIF upload lacks it, the `upload-sarif` Action back-fills it from the source files; but a raw API upload without fingerprints produces duplicate alerts. That is your lesson in one sentence: no fingerprint means every run is "all new."

Sources: [SARIF 2.1.0 spec](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html), [GitHub SARIF support](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support).

## F3. Faraday / Dradis / PlexTrac

Thin on published mechanism. Faraday (GPL, [infobyte/faraday](https://github.com/infobyte/faraday)) dedupes/merges on CVE id + service + host, with name/description/severity as the mandatory finding fields. PlexTrac (commercial) on multi-scan import into one report adds only net-new findings and attaches assets to existing ones, i.e. import-time dedup, mechanism undocumented. Dradis is report-templating first, no published cross-scan identity algorithm. None of these gives you a reusable identity spec beyond "CVE + location," which is F4's model. Sources: [Faraday Vulns docs](https://docs.faradaysec.com/Vulns/), [PlexTrac Findings docs](https://docs.plextrac.com/plextrac-documentation/product-documentation/reports/findings).

## F4. Nuclei / Trivy — native identity fields

- Nuclei: identity is `template-id` + `matched-at` (the URL/host:port where it fired). No native cross-scan dedup or diff; the documented practice is to persist per-run JSON and diff (`comm`/hash). `matched-at` is stable per location; template-id is stable per check. Good identity, but `matched-at` carries the target, so it is only stable across runs against the *same* target. Source: [Nuclei DefectDojo parser](https://docs.defectdojo.com/supported_tools/parsers/file/nuclei/), [Nuclei JSON output discussion #1916](https://github.com/projectdiscovery/nuclei/discussions/1916).
- Trivy: internal dedup key is `VulnerabilityID/PkgName/InstalledVersion`. As of issue #9793 (CLOSED) and PR #9794 (merged) Trivy now emits a `Fingerprint` field = SHA-256 of ArtifactID + Target + PkgID + VulnerabilityID, explicitly to let external systems dedupe and keep suppressions across runs, and it excludes timestamps/scan metadata by construction. This is the cleanest ready-made example of the exact pattern you want. Sources: [Trivy #9793](https://github.com/aquasecurity/trivy/issues/9793), [Trivy dedup #3274](https://github.com/aquasecurity/trivy/issues/3274), [Trivy SARIF partialFingerprints discussion #9070](https://github.com/aquasecurity/trivy/discussions/9070).

## F5. OSS you could adopt

- DefectDojo (`DefectDojo/django-DefectDojo`, BSD-3-Clause) is the adoptable reference. You do not need the Django app; you need two things from it that are data, not code: the `HASHCODE_FIELDS_PER_SCANNER` and `DEDUPLICATION_ALGORITHM_PER_PARSER` dicts in `settings.dist.py`, and the ~30-line hash routine in `dojo/utils.py` (`compute_hash_code`). Several of your Kali tools already have curated entries there (Nmap, Nuclei, Trivy, Nikto, testssl, etc.). Lift the field lists for the scanners you share, drop the Django coupling. License is compatible with almost anything.
- SARIF ecosystem: `microsoft/sarif-tools` and `microsoft/sarif-sdk` give you fingerprint/partialFingerprint handling if you standardize on SARIF, but that means writing SARIF emitters for 41 text/XML parsers — large tax for a single-file server.
- Deep Eye ([zakirkun/deep-eye](https://github.com/zakirkun/deep-eye)) advertises "fingerprint collapse" and scan-diff/retest, but it is young and unproven; treat as inspiration, not a dependency (low confidence).

Recommendation: copy DefectDojo's field-map data + hash function. Do not add a dependency.

## Deliverable (a) — best mechanism, exact fields

One fingerprint per finding: `sha256( parser_id + "|" + join(identity_fields, "|") )` where `identity_fields` is a **per-parser allowlist drawn only from a global whitelist**, mirroring DefectDojo. Concrete starting field sets for your Kali tools:

- Port/service scans (nmap, masscan-style output): `host` + `port` + `protocol` + `service_name`. Exclude banner version string, latency, scan order.
- Web/vuln checks (nuclei, nikto): `template_id`/`check_id` + `matched_url_path` (path only, query/fragment stripped) + `method`. Exclude response byte size, timing, matched payload snippet.
- TLS (testssl, sslscan): `finding_id` + `host` + `port`. Exclude cert dates, cipher-list ordering.
- CVE-bearing (trivy, searchsploit joins): `cve_id` + `pkg_name` + `component`. Exclude installed_version from *identity* but keep it in evidence (a version bump is a state change you may want to surface, not a new finding).

Global whitelist of fields identity may ever touch: check/template/rule id, host, port, protocol, path, method, cve_id, pkg_name, component_name, severity, cwe. Everything else (byte size, IP-as-observed when the host is already keyed, discovered version, response time, and above all list position) is evidence, never identity.

## Deliverable (b) — can a config-driven per-scanner map safely widen past 5 scanners?

Yes for coverage, no as a substitute for judgment, and the two are separable. DefectDojo proves the config approach scales to ~150 scanners in production. But it also proves the field lists are human-curated per scanner and still generate false-mitigation bugs on the hard cases. The safe way to widen fast without per-scanner review is to make the classifier asymmetric:

- A finding may be called FIXED only if its parser is in an explicit "identity-vetted" allowlist. For every un-vetted parser, the delta engine emits UNCHANGED or NEW or UNKNOWN, never FIXED. False FIXED is a false-remediation attestation, the one error that gets someone owned; false NEW/UNCHANGED is only noise. Bias every uncertainty toward "still there."

That inversion lets you ship all 41 parsers immediately with a conservative default identity (id + primary location), while FIXED verdicts light up parser-by-parser as you vet each one. Per-scanner human verification is unavoidable to *grant FIXED authority*; it is not required to *run the pipeline*.

## Deliverable (c) — design options with accepted limits

- O1. Fingerprint field config: a dict `IDENTITY_FIELDS_PER_PARSER` plus a global `IDENTITY_ALLOWED_FIELDS` whitelist (copy DefectDojo's two dicts). A parser can only contribute whitelisted fields; anything else is silently dropped from identity. Accepted limit: a parser mis-mapped by a human still mis-identifies; the whitelist bounds the blast radius but does not eliminate it.
- O2. Normalization layer before hashing: lowercase hostnames, strip URL query+fragment, canonicalize port as int, sort any set-valued field, drop trailing dots, resolve nothing that varies (no DNS, no timestamps). Accepted limit: over-normalization can merge two genuinely distinct findings; keep severity in the hash as the anti-merge guard DefectDojo recommends.
- O3. Confidence tiers on the verdict, not just the match: NEW, UNCHANGED, FIXED, UNKNOWN. FIXED requires (parser in vetted allowlist) AND (prior fingerprint absent from a scan that actually ran that check successfully). If the scan stage errored or timed out, absence is UNKNOWN, never FIXED. This directly kills the DefectDojo #8100/#12754 class where a failed/partial run looks like remediation.
- O4. Store evidence separately from identity. Two dicts per finding: `identity` (hashed) and `evidence` (version, byte size, banner, shown to humans, never hashed). A version change is then a first-class "changed" signal you can report without it corrupting identity.

Hard accepted ceiling to write down: for any finding where the target host controls part of the identity string (a banner-derived service name, a reflected path), a hostile or flaky target can force a fingerprint change and thus a false NEW or false FIXED. The only defense is to keep target-controlled text out of identity (matches your prior doctrine note "target-controlled text cannot carry a verdict"). Where a field must come from the target, tier it UNKNOWN on mismatch rather than FIXED.
